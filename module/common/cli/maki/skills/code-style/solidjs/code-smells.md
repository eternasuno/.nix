# SolidJS Code Smells

The detailed good practices target SolidJS 1. Verify installed runtime, compiler, router, and integrations first; do not upgrade without authorization. Combine with web-platform rules for browser behavior.

- **Incompatible framework assumptions:** compare imports and execution semantics with installed-version contracts. Check runtime/compiler generation and emitted client/server builds, not only type checks.
- **Setup snapshots mistaken for reactive reads:** trace signals and props captured in one-time component setup, destructuring, or plain spreads. Read changing values in JSX/tracked computations; accessor props need an explicit accessor contract.
- **Duplicate or overconsolidated state:** inspect synchronized signals/effects, mirrored DOM state, and unrelated fields grouped to reduce signal count. Derive values and preserve independent ownership. Signals are appropriate when they simplify genuine live dependencies or coordination; fewer signals alone is not an improvement.
- **Incorrect effect tracking or cleanup:** check synchronous dependency tracking, reads after `await`, feedback writes, registration lifetime, and owner-scoped `onCleanup`. Returning a function from `createEffect` does not register cleanup. Stale-result handling does not itself cancel requests.
- **Invalid update or transaction assumptions:** inspect in-place signal mutations, direct store writes, assumptions that signal writes are deferred, and batches crossing async gaps. Use supported store setters and `batch` where their contracts fit.
- **List identity or conditional rendering bugs:** trace insertion, removal, reordering, and item/index contracts. Choose identity- or position-based list rendering intentionally; simple inline conditions alone are not a defect.
- **Async data mirrored through effects:** compare resource sources and fetchers with actual loading, failure, refetch, and stale-content behavior. An async memo is not an automatically resolved resource. Catch event-handler and detached async errors at their own boundaries; subtree error boundaries do not cover everything.
- **Universal fixed-form machinery:** identify actual dynamic data before accepting configuration-generated business forms or mode-switched components. Compose explicit business forms and coherent controls instead.
- **Unnecessary controlled forms:** check whether values drive live reactive consumers. For submission-only data, native controls, normal names, constraints, and FormData may suffice. Preserve router-managed submission contracts and avoid per-field touched/invalid mirrors.
- **Router cache or mutation mistakes:** verify installed router compatibility, shared query identities/arguments, preload concurrency, param reads, mutation submission, and revalidation. Do not assume query or action helpers exist across all router versions.
- **SSR or security boundary violations:** inspect hydration consistency, browser-only APIs, per-user server globals, rendering resource disposal, unsafe HTML, exposed credentials, and server-side authentication/authorization. Client validation and cache keys are not security boundaries.
- **Unjustified optimization or packaging:** establish a real need before splitting, virtualizing, throttling, memoizing, or adding dependencies. Test relevant reactive changes, effect scheduling, cleanup, async transitions, SSR, and production integration rather than claiming compatibility from types alone.
